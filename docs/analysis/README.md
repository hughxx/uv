# 规则研究与自研框架设计

更新：2026-09-14。范围：当前目录内两份规则文档、两个协议样例和官方 demo 压缩包。

## 当前结论

1. 按用户要求，自研框架，不在官方 demo 上继续堆功能。本轮只分析、运行诊断、维护文档，没有修改 demo，也没有实现新框架。
2. 这是一场有生存约束的多角色资源调度、战斗和任务解题竞赛。只优化塔防会错过任务、经济和唯一宝藏；只刷积分也可能因基地先毁而输。
3. 推荐采用“有状态中央调度器 + 确定性规则内核 + 跨回合任务状态机 + 统一动作校验 + 可回放观测”的自研单进程框架。设计详见 [architecture.md](architecture.md)，这是当前建议，尚未冒称为用户确认的最终技术决策。
4. demo 的确有结构性局限，但当前没有 CPU 性能瓶颈的证据。样例决策 50 次的耗时中位数约 1.75 ms；真正已经证实的问题是信息缺失、动作资源不协调、固定角色配对和部分协议实现错误。
5. “百分百优势”只记录有明确前提的局部支配关系、确定收益和局部最优算法；不把经验战术写成必胜结论。
6. 尚不能宣称已经掌握判题器的全部实际语义。缺少判题器、真实对局回放、任务实例和《编译运行环境说明》，原始资料也有内部冲突。待确认项已单列，不会用 demo 的行为替规则补空白。
7. 2026-09-14 积分刷新已同步：完整任务得分明确为 `S+5*T/t`，部分完成为 `S*p`；原公式排版疑问已关闭。任务SOP缩短耗时的增分现在可以计算，新增G11“已确定完整答案无机会成本时尽早提交”。取整、最小合法t和完成回合记账仍待验证，见Q02。

## 证据和维护约定

- **规则明确**：资料有直接表述；不代表已经通过实际判题器验证。
- **本地复现**：在原版 demo 或样例上运行后观察到；不能外推成整场胜率。
- **静态确认**：能从代码直接确定，但没有制造完整对局来测量损失。
- **推导／建议**：写明前提、目标和适用范围。
- **待验证**：资料缺失、冲突或实际结算顺序不明确。

后续添加结论时，记录“来源、前提、反例、验证状态”。bug 使用 B 编号，策略使用 G/H 编号，歧义使用 Q 编号，边界使用 E 编号，决策使用 D 编号；编号稳定，不因修订而重排。结论被推翻时保留更正记录。

新增规则版本或真实回放后，先更新边界清单，再更新规则模型、策略证明和架构约束。下一轮协作从本页及 [decisions.md](decisions.md) 接续。
