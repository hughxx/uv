# 任务、LLM调用与世界新闻实用说明

更新：2026-09-16。依据：[接口文档](../接口文档.md)§1.3.2、§1.6–1.7、§2，以及[任务书](../任务书.md)§4.8、§5–6。当前实现问题见[真实盘面审计](framework-review.md)。

## 1. 先分清三类玩法

| 类型 | 信息来源 | 怎样兑现 | 当前自研状态 |
| --- | --- | --- | --- |
| 自进化任务 | 开拓者领取后出现`phaseTask` | 沙盒求解，`submitAnswer`提交答案 | 有通用跨轮流程，缺真实任务成功验收和SOP积累 |
| 新闻推理 | `worldNews.officialNews` | 调整采矿、囤货、卖矿等动作 | 读取现价、保存原文；尚无未来事件解释与交易策略 |
| 宝藏推理 | 多天`worldNews.folkLegends` | 凑物品、到指定位置和时间用`summonTreasure` | 有协议校验；未形成完整推理与执行闭环 |

新闻推理不是到任务点提交一段文字；看懂新闻但没有相应游戏动作，也不会自动赚钱。

## 2. 怎样接任务、做任务

1. 从`teamOur.playerTasks`选择己方任务点：检查`isValid=true`、`coldDownRounds=0`，读取奖励和`timeoutRounds`。不要把超时15轮误当成冷却15轮。
2. 开拓者走到合法相邻交互格，输出`acceptTask`。工人不能替代开拓者接任务，走到附近也不会自动领取。
3. 下一轮核对`phaseTask`是否非空；这是任务原文，不是任务点列表中的简介。接取动作输出不等于平台已经接取成功。
4. 解题期间开拓者保持在该任务点允许的驻留范围；其他工人可以继续操作。离开范围或死亡都会结束任务。
5. 根据题面决定直接求解还是执行沙盒工具；得到有依据的答案后，给开拓者输出`submitAnswer`和字符串`taskAnswer`。
6. 看后续`errors`、`phaseTask`、任务冷却、分数／金币变化，区分完整完成、部分通过、超时与失败。HTTP 200或提交动作本身都不是成功证明。

只示意动作格式，ID和答案需换成当局真实值；完整响应始终使用三个顶层字段：

```json
{"roleCommandMap":{"10011":{"action":"acceptTask"}},"prompt":"","executeCmd":""}
```

```json
{"roleCommandMap":{"10011":{"action":"submitAnswer","taskAnswer":"按题目要求生成的答案字符串"}},"prompt":"","executeCmd":""}
```

不得照抄第二条中的示例文字当答案。若题目要求JSON答案，应把该JSON序列化为`taskAnswer`字符串；当前状态机会处理模型返回的字符串／对象／列表，但最终正确格式仍由题目决定。

### 当前哪些代码在做这些事

- [`AcquireTask`](../../CoreGeek/src/agent/tasks.py)：任务点选择和接取候选。
- [`prepare_task`](../../CoreGeek/src/agent/tasks.py)：维护LLM、命令结果和答案的跨轮状态。
- [`StrategyEngine`](../../CoreGeek/src/agent/strategy.py)：让任务与其他角色动作共同参与决策。
- [`ActionCompiler`](../../CoreGeek/src/agent/actions.py)：验证角色、相邻范围、任务驻留与输出格式。

Demo缺少这套流程，真实R1–R249的任务及工具字段全空，不是平台禁止Demo做题。

## 3. 大模型究竟怎么调用

**这里使用比赛平台代调模型的接口，不是让选手服务直接调用某家模型SDK。**

```text
我方HTTP响应.prompt
    → 判题器调用平台LLM
    → 后续回合请求.llmResp
    → 我方解析，选择继续请求工具或提交答案
```

选手把问题写进响应顶层`prompt`即可请求模型；返回内容通过请求顶层`llmResp`接收。接口没有给模型型号、API地址、API Key或可选model参数，不应虚构这些配置，也不用先在当前包里添加一个外部模型SDK。平台模型具体能力／上下文长度／超时需环境资料确认。

当前实现会把题面、有限历史、剩余额度、响应格式要求和`requestId`一起放进prompt。模型返回以下两种JSON之一；这是**我们的状态机约定**，不是平台强制的LLM格式：

```json
{"requestId":"必须原样回传本次ID","kind":"execute","command":"需要沙盒执行的命令"}
```

```json
{"requestId":"必须原样回传本次ID","kind":"answer","answer":"题目要求的答案"}
```

`requestId`不匹配的旧回复不能推进当前任务。模型说“我执行过”也不算执行证据：真正执行必须发出`executeCmd`，再检查平台返回的`lastCmdResult`。

### 一次典型工具往返

以下按每种结果均在下一轮返回示意，不保证所有实际延迟相同：

| 回合 | 收到的事实 | 本轮输出 |
| --- | --- | --- |
| Rk | 任务可接，开拓者到位 | `acceptTask` |
| Rk+1 | `phaseTask`出现 | `prompt`请求LLM规划／求解 |
| Rk+2 | `llmResp`要求执行命令 | `executeCmd` |
| Rk+3 | `lastCmdResult`返回 | 检查退出码，再将结果放入新`prompt` |
| Rk+4 | `llmResp`给出有依据答案 | `submitAnswer` |
| Rk+5 | 判分／任务状态反馈 | 判断完成、部分通过或继续求解 |

模型可以直接给出可靠答案时，不必硬走沙盒。反之，缺证据时不能为了减少回合编造答案。当前三角色的游戏动作与顶层工具请求可以同时出现在响应中，但这是两个调度通道，不意味着同一角色可以同时move和attack。

### 三种限制不要混为一谈

| 限制 | 规则／实现 | 含义 |
| --- | --- | --- |
| 平台任务外LLM额度 | 每游戏日3次，R1、R131、R261…重置 | 适用于新闻等任务外用途 |
| 平台任务期间LLM额度 | 自进化任务执行期间不受上述限制，也不占日额度 | 仍受任务时间和运行规则限制，不代表能无限耗回合 |
| 当前本地工具预算 | 默认`--task-max-requests 12`，LLM与命令合计 | 自研止损上限，不是平台只允许12次LLM |

当前任务外LLM被编译层主动禁用，因为还没有日额度管理器。要接新闻模型，必须补上预算和结果关联，不能删掉校验就任意调用。也不要为了绕过日额度，长期挂着任务替别的玩法跑模型；这种用途没有明确赛事许可。

## 4. 沙盒、超时和失败怎么判断

`executeCmd`由判题器在**任务沙盒**执行，不是在运行比赛HTTP服务的目录里执行。任务沙盒不允许外网，提供基础shell／Python；具体软件版本、预置文件和本地服务以题面和环境说明为准。天气API示例也不能直接等同于调用公网天气网站。

当前包装器使用POSIX shell和`python -c`，先打印关联标记，再执行模型命令；这项依赖仍需真实任务环境核验。服务入口运行Python 3.11，并不证明另一个沙盒也有相同命令别名和软件包。

| 返回内容 | 含义 |
| --- | --- |
| `[exitCode:0]` | 进程正常退出；不等于答案正确 |
| `[exitCode:1]`等非零退出码 | 命令失败；只凭数字无法区分文件不存在、语法、依赖等原因 |
| `[TIMEOUT]` | 沙盒执行超时；保留的部分输出不等于完整结果 |
| `[JUDGER_ERROR]` | 判题器侧执行异常 |
| 尾部`[TRUNCATED]` | 输出截断，需缩小查询范围 |

命令最长15秒；HTTP请求到响应的5秒限制是另一条链路，不能在HTTP handler里阻塞等完整LLM／沙盒结果。

平台`errors[].errorCode`的1表示任务超时，2表示答案错误／不完全正确，3网络错误，4指令错误，5任务外LLM额度超限。**它和shell的exitCode不是同一套编码。**

当前日志的`decision.task`能看关联、命令序号、重复次数、退出码、`markerSeen`和白名单`errorHints`；默认不会打印题目、命令、答案或异常正文。若旧日志只保留长度，清洗脚本不能还原正文。

重复同一命令且结果不变两次后，状态机会拦第三次并要求换方法；这只防空转，不会修复错误命令。若要真正调通一道题，需要一组在本地妥善保管的`phaseTask → llmResp → executeCmd → lastCmdResult → submitAnswer → 判分反馈`证据。不要把完整题目、路径或凭据提交到公共Git。

任务时间也要单独算：本局超时15轮，到了末尾即便本地还剩请求额度，也可能来不及完成命令、后续模型和提交。该截止时间缺口尚待修复，见审计B11。

## 5. 怎样从“能做一题”变成可复用SOP

当前只有通用工具状态机，还没有经过判分验证的SOP库。建议保存的是方法而不是某一道题的答案：

1. 记录任务族、接口／文件结构和沙盒环境特征；不只比较自然语言标题。
2. 第一次探索后提取参数化步骤：定位数据、查询、校验、输出编码和答案格式。
3. 必须有平台正确性反馈才能提升可信度；失败也记录适用边界。
4. 同族新任务先验证前提，再用已验证步骤，必要时少量调用LLM补缺；前提不符立即退回通用求解。
5. 工具与答案内容仅在允许范围保存；跨局复用是否允许、如何持久化仍服从赛事规则。

完整任务分为`基础分 + 5 × 标准回合数 / 实际用时`，部分通过只得`基础分 × 通过率`，金币按奖励乘通过率。若本局80分、标准15轮的任务在5轮内完整完成，则按公式是95分；10轮完成则87.5分，取整和回合记账以平台为准。不能为了抢速度牺牲答案证据。

## 6. 世界新闻里的价格变化如何处理

### 本局这条新闻的正确时间轴

R131是第二天开始，新闻说铁矿“明日全面停工，修复约2天”。依任务书§5.1的对应示例解释：

| 时间 | 预计采集与价格影响 | 证据状态 |
| --- | --- | --- |
| 第二天 R131–R260 | 白天铁矿仍可采；现价铁3 | 日志到R249，观测现价始终为石1／铁3／铜5 |
| 第三、四天 R261–R520 | 预计铁矿停产、铁价上涨 | 规则示例支持；本局日志尚未覆盖，实际值须新请求确认 |
| 第五天起 R521+ | 预计恢复开采和原价 | 同样是该消息推导；后续消息可能改变结论 |

因此R131不应立即把铁价改高，也不能说R249还没涨就是平台故障。新闻没有给涨价倍数，不要编成“必定翻倍”。第三天的准确现价最终读取`vendorShopList`。

还有一个关键点：新闻在R131出现，R132字段已恢复空字符串。**空字符串表示这轮没有新消息，不表示上一条消息失效。** 只看最新请求、不保留带时间的新闻状态会丢掉预测窗口。

### 实现上分四层

1. **观测事实**：每轮更新`vendorShopList`、矿点位置和动作反馈；保留变化事件。现价与预测分开存。
2. **事件账本**：按`发布时间／游戏日／渠道／内容`保存新消息；抽取矿种、停采区间、价格方向、恢复条件、置信度与来源。相同文字在另一天重发，不应自动合并成同一次事件。
3. **有限预测**：相对时间“明天”锚定发布日；倍率未知就保持未知。有把握的模板用确定性解析，含糊消息才考虑LLM；模型产出的字段须校验，不能直接改钱包和现价。
4. **策略候选**：分别提出提前采铁、持有库存、按现价卖出、换铜／石、避开停采矿区等方案，由同一团队调度器比较时间、背包、资金、返防和替代收益。

使用LLM时可要求结构化输出，如`resource=iron`、`startDay=3`、`endDayExclusive=5`、`miningAvailable=false`、`priceDirection=up`、`multiplier=null`，附原文依据。这个结构是待实现的内部设计，不是平台已经提供的请求字段。

### 囤货什么时候值得

比较的是**持有并在未来卖出相对现在卖出的净增益**，不是“未来价格更高”一个条件：

```text
预期持有增益
  = 数量 ×（预期未来售价 − 当前售价）
  − 额外往返与等待成本
  − 占用背包、错过采集和升级的机会成本
  − 对返防和基地生存的影响
```

角色死亡可能推迟兑现，基地被毁可能使预期收益失去意义；不能把未来金币当现有金币花。临近入夜或必须立刻升级防守时，即使明天可能涨价也可能应该今天卖出。只有前提确定、全部成本已覆盖，才能讨论可证明的局部优势；目前材料不足以承诺无风险套利。

新闻预告停采时，不应仅因`mapInfo`里矿点还在就一直发`collect`。需要用事件窗口控制可用性，再用真实反馈修正；不能把一次碰撞或采矿失败就误记为永久停产。

## 7. 接下来怎样验收

- 先修复审计中的开火／空等基线和威胁漏项，否则赚到资源也可能无法转成有效防守。
- 在自研包中跑通一条完整任务证据链，验证正确答案反馈、错误反馈、超时和重复工具止损；Demo这249轮无法替代这个验证。
- 新闻验证至少覆盖R131发布、R132空消息保留、R261生效、R521恢复，以及后续新闻改写预测；本局只够验证前两项。
- 新闻SOP、任务SOP和收益推测均要留下前提与反例，不能把模型解读当作裁判事实。
